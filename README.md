## Назначение репозитория

Репозиторий содержит документ о концепции и границах проекта **«Интеграция Bitrix24 и Яндекс 360 для выездных инженеров»**, матрицу трассировки требований (RTM), журнал ревью и исходные материалы.

**Заказчик:** руководитель бизнес-процесса / представитель службы эксплуатации и ремонта.

**Цель работы:** формализовать ожидания заказчика, определить рамки решения и создать единый источник истины для команды разработки.

Интеграция предназначена для передачи заданий выездным инженерам через Яндекс 360 и получения результатов их работы обратно в Bitrix24. При этом Bitrix24 остаётся основной системой учёта сделок, задач и данных CRM, а Яндекс 360 используется как канал взаимодействия с инженерами, у которых нет доступа к порталу Bitrix24.

## Правила формирования коммитов

**Один коммит — одно логическое изменение.** 

**Формат сообщений:**

    <тип>: <описание с маленькой буквы, без точки>

**Типы:**

| Тип | Когда использовать |
|-----|--------------------|
| `docs` | Документация |
| `feat` | Новая функциональность или раздел |
| `fix` | Исправление ошибки |
| `chore` | Рутина: настройка, конфиги |
| `refactor` | Переработка без изменения смысла |

**Примеры допустимых:**

    docs: добавлено описание предметной области
    docs: добавлены заинтересованные стороны
    feat: добавлены сценарии использования
    fix: уточнены ограничения интеграции
    chore: добавлены шаблоны документов

**Недопустимые:**

    update
    fix
    правки
    asdf

## Как устроены ветки и ревью

Работа ведётся через **feature-ветки** с обязательным ревью.

**Схема:**

    main
    └── feature/<название-задачи>   

---

**Процесс:**

1. Автор создаёт feature-ветку от `main`.
2. Работает, коммитит, пушит.
3. Когда всё готово, создаёт **Pull Request**.
4. Ревьюер (другой участник команды) читает diff, оставляет комментарии и заполняет `review_log.md`.
5. Если Approve, автор или ответственный участник сливает PR в `main`.
6. Если Request changes, автор исправляет замечания и пушит изменения в ту же ветку, PR обновляется.
7. После merge ветка удаляется.

## Как запустить работу

**1. Клонировать репозиторий:**

    git clone https://github.com/DoctorZhдан/bitrix24-yandex360.git
    cd bitrix24-yandex360

**2. Создать рабочую ветку:**

    git checkout -b feature/название-задачи

**3. Работать, коммитить, пушить:**

    git add .
    git commit -m "docs: добавлено описание концепции"
    git push -u origin feature/case-concept

**4. Создать PR на GitHub:**

- **Compare & pull request** → base: `main`, compare: твоя ветка.
- **Reviewers:** участник команды, который проверяет изменения.
- **Create Pull Request**.
